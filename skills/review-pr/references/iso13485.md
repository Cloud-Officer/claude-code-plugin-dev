## ISO 13485:2016 — clauses a code change can affect

Tag format: `[ISO13485 <clause>]`.

- 4.1.6 Software used in the QMS — a change to a quality-system tool needs its validation re-assessed.
- 4.2.4, 4.2.5 Documents and records — quality records stay complete, legible, retained and protected from change; document versions stay controlled.
- 7.1 Risk management (ISO 14971) — code implementing a risk control measure is changed, weakened or bypassed.
- 7.3.3 Design inputs — the change traces to a requirement.
- 7.3.6 Verification — tests prove the changed requirement; acceptance criteria are covered.
- 7.3.7 Validation — user-facing behaviour changes that need re-validation.
- 7.3.8 Design transfer — build and release stay reproducible; versions pinned.
- 7.3.9 Design changes — impact on released versions, on the risk file and on other features is assessed.
- 7.4 Purchasing — new or changed third-party software (SOUP/OTS).
- 7.5.6 Process validation — changes to the CI/CD pipeline, build scripts or code generators.
- 7.5.8, 7.5.9 Identification and traceability — the software version stays identifiable at runtime and in records.
- 8.3, 8.5.2 Nonconforming product and corrective action — a fix to a released version references its problem report or CAPA.

## IEC 62304 — software lifecycle

Tag format: `[IEC62304 <clause>]`. Apply the rows for the repository's safety class and every lower class.

- Class A and up:
  - 5.2 Requirements — new behaviour has a requirement.
  - 5.7 System testing — the change is covered by system-level tests.
  - 5.8 Release — known residual anomalies documented.
  - 6, 9 Maintenance and problem resolution — fixes link to a problem report.
  - 7.4 Risk management of changes — changes are analysed for new hazards or effects on risk controls.
  - 8.1.2 SOUP identification — every new or bumped dependency is listed with name, manufacturer and exact version.
- Class B adds:
  - 5.3 Architecture — new SOUP items have stated functional and performance requirements (5.3.3, 5.3.4).
  - 5.5.3, 5.5.5 Unit verification — units have acceptance criteria and are verified.
  - 5.6 Integration testing — integration tests cover the changed interfaces.
  - 7.2, 7.3 Risk controls — software risk controls are implemented and verified by tests.
- Class C adds:
  - 5.3.5 Segregation — segregation between software items that the risk analysis relies on is kept.
  - 5.4 Detailed design — each changed unit has a detailed design.
  - 5.5.4 Additional acceptance criteria — event sequence, data and control flow, resource allocation, fault handling, initialisation, self-diagnostics, memory management, boundary conditions.

## Other medical-device requirements (US and EU)

- `[IEC81001-5-1]` Health software security lifecycle — threat model and security requirements updated for changed attack surface; secure coding.
- `[IEC62366-1]` Usability — changes to a safety-related user interface need a usability engineering update.
- `[21CFR11 11.10(e)]` Audit trails — computer-generated, time-stamped, never overwrite or hide earlier values.
- `[21CFR11 11.10(d)]`, `[21CFR11 11.10(g)]`, `[21CFR11 11.300]` Access, authority checks and ID/password controls on electronic records.
- `[21CFR11 11.50]`, `[21CFR11 11.70]` Electronic signatures — show signer, date and meaning; signature bound to its record.
- `[FDA 524B]` Cyber devices — software bill of materials (SBOM) updated for dependency changes; vulnerabilities can be patched.
- `[FDA QMSR]` 21 CFR 820 incorporates ISO 13485 — the design-control findings above also apply in the US.
- `[MDR AnnexI 17.2]` Software developed to the state of the art: lifecycle, risk management, information security, verification and validation.
- `[MDR AnnexI 17.4]` IT security measures, including protection against unauthorised access.
